X and y must have compatible shapes because when you multiply X and beta_hat together, they have to return y such that y has the same number of rows as X and one column (the column of fitted values). We include the intercept column in the X matrix because that will let the model have a non-zero intercept (the line doesn’t have to start at the origin), and that will tell us what the \(\widehat{\beta_0}\) that we calculate will be. Standardizing the predictors was done so that all of the predictors would have a common measurement scale (for instance instead of having the study hours per week be in the single digits and the other predictors be in the double digits approaching 100, they are all centered at 0 with a standard deviation of 1) which makes the coefficients more comparable and also makes the design matrix better conditioned (talked more about later). Broadcasting made this standardization possible without a Python loop because in the Z calculation, it was implied that each element in the predictors array was to be subtracted by the mean of that column, so a loop was not needed to iterate through each element in the predictors array individually, and the same is true for dividing by the sds of each column. It was implied that each element in the (predictors - mean) array was to be divided by the sds for each of the 120 rows, so a loop iterating through each element is not needed.

X @ beta_hat represents our approximation of the response values given the predictor values, so X @ beta_hat gives us the y_hat values, which are the y-values of our linear regression model. The residual mean should be near zero when an intercept is present because the least squares method forces the residuals to sum to zero as a result of how the residuals are minimized for the least squares method, with the residuals made to be orthogonal to every column in X (including the ones column). The Root Mean Square Errors (RMSE) summarizes the square root of the average squared distance between the actual measured values and the predicted values, and this is helpful as it returns an error in the original units of the response variable. The difference between X @ beta_hat and X * beta_hat is that the @ operator is matrix multiplication, whereas the * operator signifies element wise multiplication. So the * operator broadcasts beta_hat across the rows of X and will return a 120x4 array, but that is not the matrix multiplication that we want for this operation, we want mathematical matrix multiplication, which uses the @ symbol and returns one fitted value for each observation, resulting in an array of length 120 (instead of a matrix of shape 120x4).

Q @ R \(\approx\) X verifies that the design matrix X has been correctly decomposed into the components of Q and R, and when Q and R are matrix multiplied back together, they should give us back (approximately because of computational rounding) our design matrix X. Q.T @ Q \(\approx\) I verifies that the matrix Q is an orthonormal matrix, because for an orthonormal matrix Q, Q.T @ Q = I, so this is just verifying that that is true, because the QR decomposition should return Q as an orthonormal matrix. The singular values from SVD tell us how strong or weak the stretching/scaling of each predictor (the columns of X) applies along each of its orthogonal directions, with higher singular values meaning more stretching/scaling, and lower values meaning less scaling/stretching which signals that there is redudancy or near-redundancy in the columns of X. A large condition number suggests that there is some collinearity between the predictors, so there might be some redundancy in the information provided by the predictors. For this data, the condition number did very drastically change (from 1484.1694 to 1.7748) after standardization. This happened because the condition number is based on the largest singular value and the smallest singular value and this will be affected by the scaling of the units between predictors, for example if one predictor is measured in the thousands, and another is measured in single digits, the condition number will be very large. So that is why we used a standardized design matrix, so that all the predictors had very similar scales for their measurements, which means that the condition number here tells us more about whether any predictors are collinear or not. Based on this, the standardized design matrix does not show any evidence of severe-near redundancy among predictors, as the condition number for the design matrix was 1.7748, which is fairly close to 1.

Part 5 - Reproducibility and Numerical Computing Reflection

Clean execution matters a lot for a computational report as it is very important that your work is reproducible so that others can verify your work and hopefully get the same result every time, and so that others can also build off of your work and be sure that there are no problems with it. This is why it is also important that reusable code not depend on hidden notebook states, as that would make the whole report not reproducible as important variables or code would depend on something that is specific to only you and no one else. The reason np.linalg.lstsq() is preferable to manually computing \((X^TX)^{-1}X^Ty\) is because computing inverses is much less numerically stable than using the least squares method, as computing an inverse involves a lot of floating point calculations, and depending on the design matrix, can introduce a lot of rounding errors, which least squares method bypasses by using Singular Value Decomposition. Another reason is that the least squares method also works on non-square matrices, while matrix inverses require a square matrix (hence why \(X^TX\) is needed), which also squares the condition number as a result. For checking the results from SVD and QR decomposition, np.allclose() is preferable to using exact equalities because there is often computational rounding involved, so the result is approximately (within very small tolerances) equal, but often not exactly equal, even though they are equal for our purposes. The condition number comparison taught me that the scale of measurements between predictors matters, and can give you a falsely large condition number, even if the predictors have almost no collinearity. One reproducibility practice from this homework that I will carry into the final project is making sure that code runs sequentially from top to bottom, and making sure that everything runs from top to bottom without issue with a refreshed kernel so that I am sure that there are no hidden notebook states.
